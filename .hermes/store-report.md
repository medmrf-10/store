# تقرير الاستطلاع التقني لمستودع المتجر (Store)

## 1. ما هو هذا المستودع
مستودع التوزيع والنشر والإصدار العام (Release & Distribution Channel) لتطبيقات أندرويد التابعة لمشروع «إرث» (موقع المتجر: `https://medmrf-10.github.io/store/`).
تستهلكه ثلاث جهات: مستخدمو الهواتف عبر متصفح الويب (PWA وصفحات التنزيل)، وتطبيق المتجر الأصلي لأندرويد (`com.irth.store`)، والتطبيقات الموزعة ذاتها (مثل `mirath`) عبر محرك التحديث الذاتي المدمج.
يوجد مستقلاً لعزل شفرات التطبيقات البرمجية عن قناة النشر، ولتوفير فهرس كتالوج مركزي (`apps.json`) ورابط تحميل مباشر لحزم APK بعيداً عن متجر Google Play.

## 2. apps.json — المخطط الحقيقي
يحوي الملف كائناً جذرياً بمصفوفة `apps` تضم سجلات التطبيقات. وفيما يلي نموذج حقيقي منسوخ حرفياً:

```json
{
  "slug": "mirath", "name": "ميراث",
  "page": "mirath/", "icon": "mirath/icons/icon-192.png",
  "tag": "جديد", "version": "1.37", "size": "19.9 MB",
  "desc": "تطبيق «إرث» لأندرويد — مكتبة الدروس والسلاسل العلمية في جيبك، بقراءة متزامنة مع الصوت وبلا اتصال.",
  "url": "apk/mirath-1.37.apk", "vcode": 38,
  "pkg": "com.irth.mirath",
  "whatsnew": "إصلاح: تنزيل الطبقات يستمر في الخلفية حتى لو غادرت الصفحة."
}
```

### تفصيل حقول المخطط والمقارنة البرمجية
- `slug` (نص): المعرّف الفريد للتطبيق. مستهلك وظيفياً في `Update.kt` للبحث عن التطبيق (`firstOrNull { it.slug == slug }`).
- `name` (نص): اسم التطبيق العربي. يُعرض في واجهة المتجر؛ معرّف في كائن بيانات `Update.kt` ولكنه غير مستخدم منطقياً.
- `page` (نص): مسار صفحة الويب التعريفية. يُستهلك في المتجر الويب فقط؛ مهمل تماماً في `Update.kt`.
- `icon` (نص): مسار أيقونة التطبيق. يُعرض في المتجرين الأصلي والويب؛ مهمل في `Update.kt`.
- `tag` (نص): شارة ترويجية (مثل "الأصلي" أو "جديد"). شكلي؛ مهمل في `Update.kt`.
- `desc` (نص): وصف التطبيق. يُعرض في بطاقة المتجر؛ مهمل في `Update.kt`.
- `version` (نص): رقم الإصدار الظاهري للمستخدم (مثل `"1.37"`). لا يدخل في مقارنة التحديث إطلاقاً، ويُستخدم فقط كنص داخل إشعار واسم ملف التحميل `"$slug-${f.version}.apk"`.
- `size` (نص): حجم الملف التقديري (مثل `"19.9 MB"`). حقل شكلي توضيحي لا يُفحص.
- `url` (نص): المسار النسبي للحزمة APK. يُستهلك برمجياً لبدء التحميل عبر `DownloadManager`.
- `vcode` (عدد صحيح): رقم الإصدار البرمجي الداخلي (versionCode). **هذا هو الحقل الجوهري الوحيد الذي يُقارن برمجياً**:
  - في `Update.kt`: يُقارن صراحة `if (me.vcode > myVcode)`.
  - في تطبيق المتجر (`com.irth.store`): يُقارن بقيمة `packageManager.getPackageInfo(pkg).versionCode` لتحديد حالة التطبيق (`OUTDATED`).
- `pkg` (نص): معرّف الحزمة البرمجية (Application ID). يُستهلك في تطبيق المتجر الأصلي للاستعلام من النظام هل التطبيق مثبت أم لا؛ بينما يهمله `Update.kt` نهائياً.
- `whatsnew` (نص): ملاحظات الإصدار الجديد. يُعرض في نافذة المتجر الأصلي؛ مهمل في `Update.kt`.
- **حقول التجزئة والتوقيع (sha256 / checksum)**: غير موجودة نهائياً بالمخطط.

## 3. مسار النشر خطوة بخطوة

### أ) نشر إصدار جديد لتطبيق قائم (مثال: mirath 1.38)
1. بناء الحزمة في مستودع التطبيق مع رفع `versionCode` إلى `39` و `versionName` إلى `"1.38"` في `app/build.gradle.kts`.
2. نسخ الحزمة الناتجة إلى مستودع المتجر تحت المسار: `apk/mirath-1.38.apk` (التسمية القياسية: `<slug>-<version>.apk`).
3. تعديل سجل التطبيق في `apps.json`: تحديث `version` إلى `"1.38"`، و `vcode` إلى `39`، و `url` إلى `"apk/mirath-1.38.apk"`، وتحديث الحجم `size` وملاحظات `whatsnew`.
4. تحديث صفحة الهبوط إن وجدت (`mirath/index.html` بتعديل كائن `APP`؛ علماً أن هذا أُهمل تاريخياً وبقي على 1.3).
5. التحقق قبل الدفع: التأكد من صحة بناء الـ JSON عبر `jq . apps.json` ومطابقة الـ `vcode` مع الحزمة الفعلية.
6. الالتزام والدفع:
```bash
git add apk/mirath-1.38.apk apps.json
git commit -m "mirath 1.38"
git push origin main
```
7. الانتشار: يستغرق بناء ونشر صفحات GitHub من دقيقة إلى دقيقتين. كاش المتصفح الافتراضي لـ GitHub Pages هو 10 دقائق (`max-age=600`).

### ب) نشر تطبيق جديد كلياً (Brand-new App)
1. إعداد اسم المعرّف (`slug`) واسم الحزمة (`pkg`) وحفظ أيقونة التطبيق بدقة 192×192 في `icons/<slug>/icon-192.png`.
2. وضع حزمة الـ APK الأولى في `apk/<slug>-1.0.apk`.
3. إضافة كائن جديد متكامل داخل مصفوفة `apps` في `apps.json` بكافة الحقول الـ 12.
4. لإتاحته على المتجر الويب: إضافته إلى مصفوفة `APPS` في `apps.js`.
5. لإنشاء صفحة هبوط خاصة: إنشاء مجلد `<slug>/index.html` مع أصوله.
6. **تنبيه حرج لسير العمل**: سير العمل `.github/workflows/deploy.yml` ينسخ حالياً مسارات محددة بالاسم (`mirath`, `icons`, `apk`). في حال تم الاعتماد عليه، يجب إضافة اسم مجلد التطبيق الجديد صراحة داخل خطوة البناء، وإضافة `apps.json`.
7. الدفع: `git add . && git commit -m "add <slug> 1.0" && git push origin main`.

## 4. الموقع (Web Platform & PWA)
- `manifest.webmanifest`: يضبط معايير PWA للمتجر (الاتجاه RTL، الاسم "App Store"، وضع العرض `standalone`، وألوان السمة `#14110E`).
- `sw.js`: عامل الخدمة (Service Worker)؛ يقوم بالتخزين المسبق لأصول واجهة المتجر، ويتبع استراتيجية الشبكة أولاً (`NETWORK_FIRST`) لملفات الفهارس والصفحات، والكاش أولاً للصور.
- `apps.js`: مصدر بيانات واجهة الويب الحالية؛ يحوي مصفوفة `APPS` تضم تطبيق المتجر فقط (لا تضم ميراث).
- `index.html`: واجهة المتجر على الويب؛ توفر 4 مظاهر لونية (ليل، ورق، أبيض، داكن)، ولافتة لتثبيت الـ PWA عند دعم المتصفح، وتعرض بطاقات التطبيقات مع أزرار التحميل.
- **كيف يثبت مستخدم الهاتف الحزمة**:
  1. يفتح الرابط بالمتصفح ويضغط على زر تحميل APK.
  2. يُنزّل المتصفح الملف ثم يفتحه المستخدم، فيطلب أندرويد الإذن بالسماح بالتثبيت من مصادر غير معروفة للمتصفح.
  3. بعد منح الإذن، يُثبّت التطبيق محلياً عبر مثبت النظام (Package Installer).
  4. أو يمكن للمستخدم تثبيت حزمة `appstore-1.3.apk` لتتولى هي استعراض وتثبيت سائر التطبيقات مستقبلاً.

## 5. دور مجلد android/ وما يفعله mirath/
- **مجلد `android/`**: ليس وثائق ولا قالباً، بل هو **المستودع المصدري الكامل لتطبيق المتجر الأصلي** (`com.irth.store`):
  - مبني بلغة Kotlin مع واجهات Jetpack Compose و Material 3.
  - كوده الأساسي في `android/app/src/main/java/com/irth/store/MainActivity.kt`.
  - يقرأ `https://medmrf-10.github.io/store/apps.json` دورياً، ويفحص الحزم المثبتة بالنظام (`PackageManager`)، ويُظهر حالة كل تطبيق (غير مثبت، يتطلب تحديث، محدث)، ويدير التنزيل والتثبيت عبر `DownloadManager`.
  - مجلد `android/.devin/skills/`: يضم مهارات وقواعد تصميم مخصصة لوكيل Devin AI (مثل فحص الخطوط `typography-audit` وتصميم تدفق الشاشات `product-design`).
- **مجلد `mirath/`**:
  - لا توجد أي شفرة لميراث داخل `android/` إطلاقاً.
  - مجلد `mirath/` الموجود في جذر المستودع هو صفحة ويب ترويجية ثابتة (`mirath/index.html`) مع أيقوناتها لاستعراض مميزات التطبيق وتوفير رابط تحميل مباشر لنسخته.

## 6. الأرقام الحقيقية (مقاسة بأوامر الصدفة)
- **عدد التطبيقات المنشورة في الكتالوج**: 2 تطبيقين (`appstore` و `mirath`).
  - الأمر: `jq '.apps | length' apps.json`
- **عدد إصدارات APK لكل تطبيق في مجلد `apk/`**:
  - تطبيق `appstore`: 4 إصدارات (1.0 إلى 1.3).
  - تطبيق `mirath`: 38 إصداراً (1.0 إلى 1.37).
  - الإجمالي: 42 ملف APK.
  - الأمر: `ls -1 apk/appstore-*.apk | wc -l` و `ls -1 apk/mirath-*.apk | wc -l`
- **الحجم الإجمالي لحزم APK**: 753.51 ميجابايت (790,114,106 بايت).
  - الأمر: `du -sh apk/` (أظهر 754M)
- **حجم أكبر حزمة APK**: 18.19 ميجابايت (19,069,061 بايت) وهي الحزمة `mirath-1.37.apk` (ومثيلاتها 1.30-1.33 و 1.35-1.36).
  - الأمر: `ls -lS apk/ | head -2`
- **عدد الأيقونات وأبعادها**: 19 ملف PNG في كامل المستودع:
  - مجلد `icons/`: 3 ملفات بأبعاد 192×192 و 512×512 و 1024×1024.
  - مجلد `mirath/`: 4 ملفات بأبعاد 192×192 و 512×512 و 512×512 (قناع) و 1024×1024.
  - مجلد `android/app/src/main/res/`: 12 أيقونة موزعة على كثافات العرض (72×72، 96×96، 144×144، 192×192).
  - الأمر: `python3 -c "from PIL import Image; ..."` و `find . -name '*.png' | wc -l`
- **حجم المستودع مقابل حجم .git**:
  - مساحة المستودع الكلية على القرص: 864 ميجابايت.
  - حجم دليل `.git`: 105 ميجابايت (علماً أن النسخة مستنسخة بسجل ضحل shallow بعمق 20؛ والتاريخ الكامل في المستودع البعيد يتجاوز 800 ميجابايت).
  - الأمر: `du -sh . .git`

## 7. الثغرات والمخاطر
1. **تضخم تاريخ Git بالملفات الثنائية (Git Binary Bloat)**:
   دفع ملفات APK بحجم 19 ميجابايت مع كل إصدار رفع حجم المستودع إلى 864 ميجابايت (منها 754 ميجابايت حزم قديمة غير مستخدمة). هذا يهدد بالاصطدام بحدود سعة GitHub ويجعل عمليات السحب والاستنساخ بطيئة جداً.
2. **خلل جوهري في سير العمل `.github/workflows/deploy.yml`**:
   خطوة التجهيز في الإجراء تجمع الأصول بأمر: `cp apps.js manifest.webmanifest sw.js dist/` مع **إسقاط تام لملف `apps.json`**. الموقع يعمل حالياً فقط لأن صفحات GitHub مضبوطة على نمط النشر القديم (Legacy branch deploy من جذر `main`) وليس نمط Workflow Artifacts. لو فُعّل سير العمل لانقطعت التحديثات فوراً بخطأ 404.
3. **تشتت مصدر الحقيقة وانفصال الكتالوج (Catalog Drift)**:
   المتجر الويب يقرأ من `apps.js` (يحوي App Store فقط)، والمتجر الأصلي يقرأ `apps.json`، بينما صفحة `mirath/index.html` تحوي كائناً ثابتاً متجمداً على الإصدار `1.3` برابط `mirath-1.3.apk` المتخلف عن الواقع بـ 34 إصداراً.
4. **غياب الأتمتة واعتماد النشر اليدوي بنسبة 100%**:
   لا توجد أي إجراءات CI/CD للتحقق من سلامة بناء الحزم، أو استخراج `versionCode` آلياً، أو اختبار صحة بنية JSON قبل الدفع، مما يفتح الباب لأخطاء بشرية تعطل التحديث التلقائي لكافة الهواتف.
5. **انعدام التحقق الأمني من التجزئة والتوقيع (No SHA-256 Checksum)**:
   يقوم تطبيق `mirath` (`Update.kt`) بتنزيل الحزمة وتنفيذ أمر التثبيت مباشرة دون فحص مطابقة البصمة الرقمية (Checksum) للملف المنزَّل، مما يجعله عرضة لتحميل حزم تالفة نتيجة انقطاع الاتصال أو هجمات التلاعب بالشبكة.
6. **كاش GitHub Pages وتأخر التحديث**:
   ضبط ترويسة الكاش على `max-age=600` (10 دقائق) يؤخر وصول إشعار التحديث للأجهزة بعد الدفع.
7. **استهلاك النطاق الترددي واستضافة الملفات الثنائية (Pages CDN Limits)**:
   استضافة ملفات بحجم 20 ميجابايت على GitHub Pages يخالف الاستخدام الأمثل للخدمة ذات الحد التقديري البالغ 100GB شهرياً، حيث تكفي 5000 عملية تنزيل فقط لاستنفاد النطاق الشهري بالكامل.

## 8. التوصيات (أعلى 5 إجراءات قيمة)
1. **ترحيل حزم APK الثنائية إلى GitHub Releases**:
   رفع ملفات الحزم إلى إطلاقات GitHub Releases والحفاظ على الروابط داخل `apps.json`، مع تنظيف مجلد `apk/` بأداة `git-filter-repo`؛ مما يُقلص حجم المستودع إلى أقل من 20 ميجابايت ويستفيد من شبكة توزيع سريعة مخصصة للملفات الكبيرة.
2. **توحيد مصدر البيانات (Single Source of Truth)**:
   إلغاء ملف `apps.js` نهائياً، وجعل كل من `index.html` وصفحات الهبوط مثل `mirath/index.html` تقرأ وتستعلم ديناميكياً من `apps.json` باستخدام الـ `slug` الخاص بها لمنع أي تفاوت مستقبلي في أرقام الإصدارات والروابط.
3. **أتمتة دورة النشر وتصحيح `deploy.yml`**:
   تصحيح ملف الإجراءات بنسخ `apps.json` وجميع المجلدات، وإنشاء إجراء آلي (GitHub Action) يُفعل عند وسم إصدار جديد (Tag)؛ ليتولى بناء الحزمة، واستخراج رقم وحجم الإصدار عبر `apkanalyzer`، وحساب الـ SHA-256، وتحديث `apps.json` ودفعها آلياً.
4. **إضافة بصمة SHA-256 في الكتالوج والتحقق منها برمجياً**:
   إضافة حقل `"sha256"` لكل تطبيق في `apps.json`، وتعديل `Update.kt` وتطبيق المتجر ليقوما بحساب بصمة الملف المحمّل ومطابقتها قبل استدعاء مثبت أندرويد لمنع تثبيت الملفات المعطوبة.
5. **فصل كود تطبيق المتجر وتطهير المستودع**:
   نقل مشروع أندرويد الأصلي `android/` إلى مستودع منفصل أو حزمة مستقلة مع إزالة مجلدات مهارات الذكاء الاصطناعي (`.devin/skills/`) من مستودع الاستضافة؛ لتقتصر مهمة هذا المستودع حصراً على كونه واجهة ثابتة للتوزيع.
